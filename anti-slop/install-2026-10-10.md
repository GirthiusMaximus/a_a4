## One deliberate deviation from the packaged files

`rules/antislop.md` and `rules/antislop.mdc` ship listing all six skills. The single line

```
- Copy & text: skills/antislop-copywriting/SKILL.md
```

was removed from both installed copies, because the pointer block is the source of truth for which skills are installed (wizard note, step 5/6) and an always-on rule must not point at a file that does not exist. `AntiSlop/rules/` keeps the unmodified originals. Everything else is byte-identical to the release.

## Entry file (wizard step 5)

No `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` existed, so `AGENTS.md` was **created** with the `<!-- antislop:start -->` … `<!-- antislop:end -->` block appended; existing content was not modified. Skill lines list only the four installed skills. The entry file is read at session start, so the pointer takes effect from the **next** session; this session applies the rules directly.

If a tool reads a different entry file, append the same marked block to `CLAUDE.md` / `GEMINI.md`. The shared markers mean the last install path run replaces the block instead of duplicating it.

## Addendum, same day: sandbox reset and what it cost

The workspace was recycled between turns. Everything outside the repo root did not survive: `~/.config/antislop/settings.json` and the Python venv were both gone. Both were recreated, `{"mode":"after"}` is in place again, and the venv now lives at `.venv` inside the repo, which is ignored by both `.gitignore` and the snapshot rules, so it is expected to be rebuilt per session with `python3 -m venv .venv && .venv/bin/pip install -r tools/skinprobe/requirements.txt`.

Lesson recorded here because it applies to the antislop install itself: the global preference file is the one piece of this install that cannot live in the repo, since agents outside this checkout read it from the platform path. On a volatile sandbox it needs re-creating per session, and only the pointer block and the skill folders can be trusted to persist.
